# Spec: 工作台重构 —— 资料库 / 剪辑室 / 首页（m2-workspace）

> 来源：2026-09-30 用户口述需求（10 点，原话见 §0.0）｜方案与用户确认（同日，"按这个方案来"）
> 依赖：m1a-ytdlp-pipeline（下载管线 / jobs / SSE / 入库 / 判重 / 封面）、m1c-video-clip（视频素材 / 剪辑 job / Range）
> 关系：本切片把 PRD §6.1 里规划的 **S5 剪辑工作台** 与 **S6 音频库完善** 重新按用户心智分组为三块（资料库=下载、剪辑室=编辑、首页=仪表盘），并把 PRD §4.2 的 **EditSpec 多段能力**取其最小版（只做 segments，不做 effects）提前落地。
> 状态：**已过 3 轮多透镜评审**（明细见 §0.12）；视频下载已由 Owner 裁决为**方案 A（一次一集）**，歧义已消除；**待用户过目本 spec → 进入 writing-plans**。

## 0.0 为什么

用户 2026-09-30 原话（按原文分点，不改写）：

> 1. 为什么内容区去的顶部空了一段？…这里本来就可以了用来访标题，平台 logo，而下面一行，则可以用来做工具栏
> 2. 我觉得获取下面就是获取视频，现在把获取和剪辑放一起了，我认为这个定位就混乱了…下载就是下载，剪辑是剪辑
> 3. 音频里面，在获得多集的情况下，是会显示多级的，但是现在视频没有了…我觉得你也可以借鉴一下音频的下载逻辑
> 4. 音频这个 tab 不需要了…整个音视频切换的 tab 栏都不需要了
> 5. 别叫获取了，叫资料库吧
> 6. 音频库…改成剪辑室吧。媒体默认剧集分组。媒体列表…多加一个视频封面，点击编辑进入这个音视频的剪辑详情页
> 7. 现在的剪辑太过于粗糙了，视频、音轨和画轨要同时可以显示
> 8. 这个页面要有保存，保存内容就是剪辑的所有时间点。现在只有一对剪辑点…可以有多个，到时候导出的可以分多段导出，也可以多段合成一段
> 9. 首页，显示 Top3 的正在编辑的媒体…还有显示 Top3 的最近下载的媒体
> 10. 整体的 body 上的滚动都不需要，所有的滚动只能在各自的容器内进行

拆开的**三个真痛点**：

1. **页面职责混乱**：下载和剪辑挤在一个页面、用一个"音视频"开关切；用户要的是"下载归下载、编辑归编辑"。
2. **剪辑太浅**：只有一对起止点、只有音频、看不到画面、没有保存 —— 用户要的是"画面 + 音轨 + 画轨同屏、多个剪辑点、能存下来"。
3. **入口分散**：没有"我最近在弄什么"的落点 —— 用户要首页两块 Top3。

## 0.1 已实测确认的前提（2026-09-30 读码核实）

1. **顶层已锁 body 不滚**：`layouts/index.tsx` 根节点 `height:100vh / overflow:hidden`，但**内容区是 `overflowY:auto`** —— 也就是"最后一层还是靠一个公共容器滚"，不是各页自管。设置页（`settings.tsx`）与首页（`index.tsx`）根本没有自己的滚动容器，全靠它。（对应需求 10）
2. **顶部空一段的根因**：`acquire.tsx:203-211` 里顶部先单独占一行放**左对齐**的 Segmented（"下载音频｜视频预览剪音频"，约 12+32+8 ≈ 52px），它右边整片空着；再往下才是"左列表 + 右内容"，右内容自己又加 16px 内边距（`acquire.tsx:233`）。两段叠一起 = 顶部约 68px 只放了一个小控件。（对应需求 1）
3. **封面已是现成设施**：`covers.ts` 按来源 id 落盘 `covers/cover-<importId>.<ext>`，`GET /api/imports/:id/cover` 已通；剪辑室卡片与首页都能直接复用，不用新建。
4. **一个来源一份视频素材**：`source_videos.import_id` 与 `imported_sources.id` **一对一**（`schema.ts:55-61`），素材文件名恒为 `media-<importId>.<ext>`（m1c §0.4 第 5 条）→ **同一来源下多集视频会互相覆盖，只会剩下最后一集**。这条直接决定了 §0.2「已裁决」的"一次只选一集"。
5. **剪辑产物和下载音频现在无法区分**：`ingest.ts:14` 把 `source_type` **硬编码成 `'download'`**；`clip-job.ts:78` 也走它 → 库里"剪出来的音频"和"下载的原音频"长得一模一样。首页要分"最近下载"和"正在编辑"，**必须先修这个**。（对应需求 9）
6. **`audio_items` 的血缘设计已落地（2026-10-01，spec `2026-10-01-audio-lineage.md`）**：血缘走新增列 `source_import_id`（指向 `imported_sources.id`），下载/剪辑/导出三条入库路径都写它。`parent_id` 仍未使用（保留给未来"从音频剪音频"）。
7. **PRD 已定波形库是 wavesurfer.js v7（ADR-6）**，且 `EditSpec` 已经是"多段数组"结构（PRD §4.2）。本切片沿用"多段"语义，但**波形/画轨改为服务端 ffmpeg 出图**，理由见 D6。
8. **ffmpeg 是硬前置**（m1c D16）：剪辑类功能没有 ffmpeg 整体不可用。本切片只加更多 ffmpeg 依赖，不改变这条。
9. **SQLite 的列默认值只在 INSERT 生效**：`updated_at TEXT DEFAULT (datetime('now'))` 这类写法，UPDATE 时**不会**自动刷新——任何"按更新时间排序"的字段都必须在代码里显式写。（对应 D13，评审发现）

## 0.2 核心决定（不可违反）

| # | 决定 | 理由 |
|---|---|---|
| D1 | **页面地图**：首页 `/`、**资料库 `/library`**、**剪辑室 `/studio`**、**剪辑详情 `/studio/:importId`**、设置 `/settings`。导航四项，**删除"音频/视频"切换器** | 需求 4/5/6。`/library` 路径沿用（原音频库），语义变为"资料库"；hash 路由，无历史书签负担 |
| D2 | **统一页面头（两行）**：第 ① 行 = 平台 logo + 标题 + 元信息（时长/集数）；第 ② 行 = 工具栏。抽成共用组件 `PageHeader`，**固定在顶部不随内容滚**。资料库 / 剪辑室 / 剪辑详情三页都用它。**资料库是双栏页——它的页面头属于「右栏」，不是整页**（2026-09-30 修正：原挂在整页顶部会横跨左列表上方）。设置页**并未引用** `PageHeader`（它是一摞 `Card`）；原稿"设置页用它的简化形态"与实况不符，已扫正 | 需求 1。用掉那条只放小控件的横带；各页同一模式，用户学一次就够 |
| D3 | **各页自管滚动**：layout 内容区从 `overflowY:auto` 改为 `overflow:hidden`；每页根容器 `height:100% / minHeight:0` + 自己的滚动容器。设置页也要有自己的滚动容器 | 需求 10。公共容器滚动会让页面头跟着滚走（与 D2 冲突），且无法逐页控制"哪块滚、哪块钉住" |
| D4 | **资料库 = 只负责下载视频素材**（一次一集，方案 A）。剪辑从资料库移出；**音频一律从剪辑获得，不提供独立音频下载入口**（服务端 `produce='audio'` 管线保留休眠，API/重试可用；UI 的格式选择与多选批量流移除）——2026-09-30 用户二次裁决："都集成到视频类型里面"，原"工具栏产物类型 Radio"取消 | 需求 2/4 的完整版。用户原话即"整个音视频切换的 tab 栏都不需要了"；视频优先工作流（下素材→剪→音频进剪辑室）成立后，独立音频下载属冗余；批量音频场景让位于该工作流 |
| D5 | **视频下载补课**：视频模式恢复**集数网格**（现在没有），并复用音频那套「逐条提交 → 两段式进度 → 汇总」体验。**一次只选一集**（已裁决方案 A）；重复下载同一来源的视频 = 覆盖（沿用 m1c：不弹确认） | 需求 3 + §0.1 事实 4。⚠️ **这是对用户原话的一处收窄**（原话是"借鉴音频的下载逻辑"，音频是批量多选）；收窄的理由见「已裁决」段 |
| D6 | **剪辑详情的时间轴改为服务端出图 + 自绘交互**：波形（音轨）与胶片条（画轨）由服务端 ffmpeg 生成 PNG 并缓存到 `<数据目录>/derived/`；前端只画时间尺 + 铺图 + 选区块，交互用 pointer events 自绘 | 需求 7。**不选 wavesurfer 做主体**：① 它只管音频，满足不了"画面轨 + 音轨同屏"；② 我们的素材是 mp4，浏览器端 `decodeAudioData` 解 mp4 容器有兼容风险，而服务端 ffmpeg 出图最稳、可缓存、可复用。PRD ADR-6 仍然有效，但**降级为"若将来需要波形缩放/精细 scrub 再引入"**（记 B2） |
| D7 | **新增"剪辑工程 + 剪辑段"两张表**：`clip_projects`（按 `import_id` 唯一 —— 一个媒体一个工程）、`clip_segments`（一个工程多段，每段 start/end/label/顺序）。工程页的"保存"= 全量替换该工程的段 | 需求 8。现在只有一对起止点是无处可存的；多段必须结构化 |
| D8 | **剪辑产物修正为 `source_type='edit'`**（现在错记成 `'download'`，见 §0.1 事实 5）。做法：给 `ingestDownloadedFile` 加可选 `sourceType` 参数（默认 `'download'` 不动老路径），剪辑路径传 `'edit'`。**不给 `audio_items` 加列**；历史错标数据按 §0.4 一次性纠正 | 需求 9。这是"最近下载"能过滤掉剪辑产物的前提；也是修一个已有的语义缺陷 |
| D9 | **导出复用既有 job + ffmpeg 编译**：新增 job kind `ffmpeg_export`，payload 存 `{ importId, segments, mode, format, quality }`；`mode='separate'` 每段一条音频入库，`mode='merge'` 用 concat 拼成一条入库。产物仍走 `ingestDownloadedFile`（sourceType='edit'） | 需求 8。与 m1c 的 `ffmpeg_clip` 同族；多段拼接是 ffmpeg 在行的活，不需要前端渲染 |
| D10 | **首页 = 两块 Top3**：`正在编辑` = `clip_projects` 按 `updated_at` 倒序取 3；`最近下载` = `audio_items` 里 `source_type='download'`，**按来源去重后**取最近 3 个作品 | 需求 9。去重理由见 §0.3 |
| D11 | **改名要全站扫一遍**（含：空态文案、`Modal.confirm` 标题、服务端 `error.next` 提示、设置页说明、代码注释）。落地后按仓库规则再跑一次"扫所有声明它的地方" | 用户要求"不要遗漏"；仓库规则明写"落地后回头扫一遍所有声明它的地方" |
| D12 | **剪辑室默认"剧集分组"视图**（现状默认是"平铺"） | 需求 6。剪辑室的主体是"媒体（作品）"，分组才符合心智 |
| D13 | **`clip_projects.updated_at` 必须由代码显式写入**（创建时、每次 PUT 保存时都写 `datetime('now')`） | §0.1 事实 9。首页"最近在编辑"直接按它排序——不显式写就永远停在创建那一刻（评审盲点） |
| D14 | **派生图（波形/胶片）固定尺寸 + 原子落盘**：固定 `w=1600 / count=12` 生成一套缓存，前端用 CSS 拉伸适配容器；生成走「临时名 → rename」，命中判定 = 文件存在且 `size > 0` | 评审盲点。① 按容器宽度生成会有无数份缓存（磁盘膨胀）；② 直接写最终路径，两个请求同时进来会互相写坏；③ ffmpeg 中断留下的半张图会被当成有效缓存**永久命中**（与 `covers.ts` 踩过的"旧扩展名随机命中"同族） |
| D15 | **导出以请求体为准**：`POST .../export` 的 `segments` **必传**（就是界面上当前看到的段），服务端不读 DB 里的工程；导出**不自动保存**工程 | 评审盲点。"改了段但没保存就点导出"必须有确定语义——用当前看到的，才符合直觉；顺带让"保存"与"导出"两件事互不隐式影响 |
| D16 | **新链路一律留日志**（仓库铁律）：派生图「生成开始 / 命中缓存 / 失败（带 stderr 尾行）」、工程「保存 / 删除」、导出 job「created / done / 失败」 | 仓库规则《Electron 前后端开发：关键步骤必须加日志》——不然"点导出没反应"这类问题无法定位 |
| D17 | **没有视频素材时不进空编辑器**：`/studio/:importId` 若该来源没有 `source_videos` 行 → 显示明确空态"这个来源还没有视频素材" + 一键跳资料库下视频；剪辑室里这类来源的"编辑"按钮**禁用并给 tooltip** | 评审盲点。用户完全可以只下音频不下视频，此时"进入剪辑"没有可剪的东西 |
| D18 | **`PUT /api/projects/:importId` 的"全量替换"必须包在**一个事务**里**（删旧段 + 写新段 + 更新 `updated_at` 一起提交，失败整体回滚） | 评审盲点（第 2 轮）。全量替换 = 先删后插；不包事务时，插入失败/进程崩溃会让用户**一次丢光所有剪辑点**——比"没保存成功"严重得多 |
| D19 | **换集会作废已保存的剪辑点，必须先确认再清**：当视频素材的 `entry_index` **发生变化**（换到另一集）时，该来源的剪辑工程要被清空；换集前弹二次确认，文案说清"已保存的 N 个剪辑点对应的是原来那一集的画面，换集后对不上，会被清掉"<br>**同一集重下（只换清晰度）不动工程** —— 时长基本一致，打点仍然有效 | 评审盲点（第 3 轮，由方案 A 引入）。剪辑点只是"时间数字"，脱离原来那一集的画面就没有意义；素材槽只有一个，换集后旧剪辑点会在**另一集的画面**上被显示出来——用户看到的是一堆对不上的标记。宁可清掉并说清楚，也不要留一堆错的 |
| D20 | **界面上要能看到"当前素材是哪一集"**：资料库视频模式的集数网格里，**已下素材的那一集要高亮标出**；剪辑详情的页面头显示"第 N 集"（单视频不显示） | 方案 A 的必然结果——素材槽只有一个，用户必须一眼知道现在手里是哪一集的画面，否则"我下的到底是第几集"会一直犯迷糊 |

### 已裁决（2026-09-30，Owner 定）

**视频一次只选一集 —— 采用方案 A。**

- 集数网格照常显示（用户要看到有哪些集）；点某一集 → 下载/替换该集的视频素材；**当前手里是哪一集，在网格里高亮标出**（D20）。
- `source_videos` 增一列 `entry_index`：记住"这份素材是哪一集"（单视频为 `NULL`）。
- 换集前要二次确认，并清空该来源的剪辑工程（D19）。
- **方案 B（按集一份素材 + 批量下载）不实施**，记 B6（触发信号：用户明确要求一次下多集视频）。
- 收窄的理由：这个工具的目的是"用画面定位、把音频剪出来"，一次只需要一集的画面；勾 193 集会下几十 GB，现实中不会这么用。等到真有批量需求，再按 B 改造。

## 0.3 页面地图与服务端契约（新增/变更）

### 页面

| 页面 | 路由 | 职责 |
|---|---|---|
| 首页 | `/` | 仪表盘：Top3 正在编辑 + Top3 最近下载（今天是"后端健康检查"，要整个换掉） |
| 资料库 | `/library` | 只下载：左来源列表 + 右（页面头 + 工具栏 + 集数网格 + 进度） |
| 剪辑室 | `/studio` | 媒体（作品）列表，默认分组；卡片/行带封面、试听、"编辑"入口（今天叫音频库） |
| 剪辑详情 | `/studio/:importId` | 一个媒体的剪辑工程：预览 + 时间轴（画轨/音轨）+ 多剪辑段 + 保存 + 导出（新增） |
| 设置 | `/settings` | 不变（只加自己的滚动容器 + 文案改名） |

### 接口（只列新增/变更；错误形状沿用 `{ ok:false, error:{ code, message, next } }`，鉴权沿用 query token / 本机 origin / 本机 Referer 口径）

**派生图（新）**

- `GET /api/media/:importId/waveform` → PNG 波形图（音轨底图）。ffmpeg `showwavespic` 生成。**尺寸固定 1600×120**，不接受来自前端的宽高（D14）
- `GET /api/media/:importId/filmstrip` → PNG 胶片条（画轨底图）。ffmpeg 抽 12 帧 + `tile` 拼接，**尺寸固定 1600×90**
- 生成：若 `derived/` 里已有且 `size > 0` → 直接回文件（记 debug 日志「命中缓存」）；否则写**临时名**再 `rename` 到最终名（D14），并记 info 日志
- 失败（ffmpeg 缺失/素材缺失/非图片产物）→ 404 或 500，**带 stderr 尾行摘要**（仓库铁律）
- 两者都要在 `index.ts` 的 `onRequest` 守卫里**豁免**（`<img>` 带不了 header，同 `/cover` 那次的漏网）
- 素材行不存在 / 文件不在盘上 → 404 `FILE_MISSING`（复用 m1c 口径）
- **图↔时间映射（写死并写进代码注释）**：图宽 1600 ↔ 时间区间 `[0, duration]`；前端点击第 x 像素 → `t = x / 1600 * duration`
  - `duration` 以**前端 `<video>` 元素的 `duration`** 为准（播放头、打点、点击换算全在它身上，只有一处真相）；服务端出图时按"整幅图铺满素材全程"生成，两端天然对齐。**不引入服务端 ffprobe 的时长作为第二份真相**——两者不一致时以视频元素为准
  - 窗口窄时图会被 CSS 压缩，像素精度随之下降（可接受，记 B8）

**剪辑工程（新）**

- `GET /api/projects` → `{ ok, projects:[{ import_id, name, updated_at, segment_count }] }`（`updated_at` 新→旧）
  - 封面/标题由前端用已有的 `coverUrl(import_id)` 与来源信息取，**接口不重复回远端缩略图地址**（避免"第二份真相"）
- `GET /api/projects/:importId` → `{ ok, project: { import_id, name, updated_at, segments:[{ id, start_sec, end_sec, label, sort_order }] } | null }`
  - 来源存在但**没有工程** → 200 + `project: null`（正常，不算错；前端按"空工程"渲染）
  - 来源不存在 → 404
- `PUT /api/projects/:importId` → body `{ name?, segments:[{ start_sec, end_sec, label? }] }` → **全量替换**；返回保存后的工程
  - 校验：`segments` 必须是数组；每段 `start_sec ≥ 0` 且 `end_sec > start_sec`；**段数上限 50**；`label` 可空、长度上限 100
  - `end_sec` **允许超过素材时长**（与 m1c 对 clip 的宽容一致：用户在末尾附近打点很容易打过头）；实际截断发生在导出时，并由导出留痕（"请求区间 X–Y，实际产出 Z 秒"）
  - 来源不存在 → 404，`error.next` 明写"该来源已被删除，无法保存"（评审盲点：不能在来源被删后让用户只看到裸 404）
  - 无工程则创建，**有则更新并显式写 `updated_at`**（D13）；`segments: []` = 清空所有段（合法）
  - **整段替换必须在一个事务里**（D18）：删旧段 + 写新段 + 更新 `updated_at` 同进同出；任一步失败整体回滚，**旧段保持不变**
- `DELETE /api/projects/:importId` → 删工程与其段（**不删**素材、**不删**已导出的音频）。**幂等**：工程不存在 → 200 `{ ok:true, deleted:0 }`
- `POST /api/projects/:importId/export` → body `{ mode:'separate'|'merge', format:'mp3'|'m4a'|'wav', quality?, segments:[{ start_sec, end_sec, label? }] }` → 201 `{ ok, jobId }`
  - `segments` **必传**（D15）；`mode` 非二者之一 → 400；`format` 白名单 → 400（复用 m1c 口径）
  - `separate`：每段一条音频入库，标题 `前缀 [mm:ss-mm:ss]`（沿用 m1c D8 的后端拼时间段）
  - `merge`：按数组顺序拼接成一条，标题 `前缀 [共N段]`
  - **标题前缀由服务端定**：取工程 `name`，工程没名字则取来源标题（前端传什么都不影响前缀，与 m1c D8 同口径）
  - **不加判重**：同一段重复导出会得到两条（文件名带各自 id8），与 m1c 对 clip 的处置一致
  - 走 `jobs` + SSE，前端 `subscribeJob` 复用（`onDone` 仍是 audio 支）
  - `ffmpeg_export` 的 retry：payload 里存的是**素材绝对路径** → 重试前校验素材仍在，不在则明确失败（同 m1c）

**其它**

- `GET /api/home` → `{ ok, editing: [...], recent: [...] }`
  - `editing` = `clip_projects` 按 `updated_at` 倒序 3 条，元素 `{ import_id, name, site, updated_at, segment_count }`（`site` 供前端画平台 logo；形状与 `GET /api/projects` 对齐，前端复用同一渲染）
  - `recent` = **按来源去重后**最近下载的 3 个作品：同一来源下多集只算一条，取该来源最新一条音频的时间与信息。元素 `{ import_id, title, site, latest_audio_id, created_at }`
    - 去重理由：一个合集刚下 193 集，若不去重，Top3 全是同一部作品的三集，首页等于没信息
  - 两边都排除 `import_id` 为 `null` 的条目（录制/无来源的音频不属于"媒体作品"）
- `GET /api/imports` **追加**两个布尔：`has_video`、`has_project`（join `source_videos` / `clip_projects`）—— 资料库与剪辑室都要用，避免前端逐条再查

## 0.4 数据模型增量

```sql
-- 剪辑工程:与来源一对一(一个媒体一个工程)。刻意不写 REFERENCES —— 级联不生效(同 m1c §0.1 事实 6),靠显式删
CREATE TABLE IF NOT EXISTS clip_projects (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  import_id INTEGER NOT NULL UNIQUE,
  name TEXT,                                   -- 缺省显示来源标题,存了就以它为准
  created_at TEXT NOT NULL DEFAULT (datetime('now')),
  updated_at TEXT NOT NULL DEFAULT (datetime('now'))  -- 注意:UPDATE 不会自动刷新,必须代码显式写(D13)
);
-- 剪辑段:一个工程多段。start/end 用 REAL 秒(与 m1c 的 0.1s 精度一致)
CREATE TABLE IF NOT EXISTS clip_segments (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  project_id INTEGER NOT NULL,
  start_sec REAL NOT NULL,
  end_sec REAL NOT NULL,
  label TEXT,
  sort_order INTEGER NOT NULL DEFAULT 0,
  created_at TEXT NOT NULL DEFAULT (datetime('now'))
);
CREATE INDEX IF NOT EXISTS idx_clip_segments_project ON clip_segments(project_id, sort_order);
```

- 两张都是新表，`initSchema` 里 `CREATE TABLE IF NOT EXISTS` 即可，无需补列
- **`source_videos` 用既有的 `ensureColumns` 幂等补一列 `entry_index INTEGER`**（记录"这份素材是哪一集"；单视频为 `NULL`）。**不动主键**（方案 A：素材仍是"一个来源一份"）
- `audio_items` **不加列**（D8 靠 `source_type='edit'` 区分）

**历史数据一次性纠正（D8 附）**

库里已存在的剪辑产物，因 `ingest.ts` 的历史硬编码，`source_type` 都是 `'download'`。它们**可判别**：标题由后端强制拼、恒以 `[mm:ss-mm:ss]` 结尾（m1c D8）。

- 用 **`LIKE`**，不用 `GLOB`：`GLOB` 里 `[` 是**字符类起始**、不是转义，写成 `'*\[??:??-??:??\]'` 会失效或误匹配；`LIKE` 只把 `%` `_` 当通配，方括号是普通字符 —— 正好合用
- 分钟位数**不能写死两位**：`mmss()` 用 `String(m).padStart(2,'0')`，≥100 分钟的素材会产出 `[120:00-121:00]` 这样的三段分钟，两位模式会漏
- 落地 SQL（`initSchema` 里执行一次，重复执行无副作用）：
  ```sql
  UPDATE audio_items SET source_type='edit'
   WHERE source_type='download'
     AND title LIKE '%[__:__-__:__]'      -- 形如 [05:12-06:03]
     OR (source_type='download' AND title GLOB '*[0-9][0-9][0-9]:[0-9][0-9]-[0-9][0-9][0-9]:[0-9][0-9]]');  -- 三位分钟:形如 [120:00-121:30]
  ```
  （两段：常见的两位分钟用 `LIKE`；三位分钟用 `GLOB` 的纯数字字符类显式匹配。**必须配单测**，见 §0.6）
  - **注记（2026-09-30 P4 落地修正，Ruling P4-6）**：`GLOB` 模式**末尾必须补一个字面量 `]`**（写作 `…]]`）——`GLOB` 是**整串匹配**，而剪辑产物标题**恒以 `]` 结尾**（`[mm:ss-mm:ss]`）；漏掉收尾 `]` 会让三位分钟（如 `[120:00-121:30]`）**不命中**，直接违反 §0.7「三位分钟命中」的测试要求。实现的准确文本见 `server/src/db/schema.ts` 的 `db.exec`
- 已知可接受的误伤：用户手动取的标题恰好以 `[00:00-00:00]` 形式结尾 —— 概率极低，且改错只影响"最近下载"的筛选，可接受（记 B7）

**级联与缓存**

- `DELETE /api/imports/:id` 必须**显式级联删** `clip_projects` 与其 `clip_segments`、`source_videos` 行与素材文件（现在只删来源行 + 素材，见 m1c §0.4；本轮把工程也纳入）
- 派生图落 `<数据目录>/derived/`，文件名 `wave-<importId>.png` / `film-<importId>.png`（**固定尺寸，所以不带尺寸后缀**，一套一份）。**是可再生缓存**，来源删除时尽力清理、失败只记日志（同 `covers/` 的定性）
- **素材本身一变，派生图必须作废**（R3-2）：**替换素材**（换集 / 换清晰度 / 重下）或**删除素材**时，一并删掉该 importId 的 `wave-<id>.png` 与 `film-<id>.png`，下次访问重新生成。理由：派生图的内容**完全由那一份素材决定**，不清就会拿**上一集的波形/画面**冒充新素材的缓存（与 `covers.ts` 的"旧图随机命中"同族）。删失败只记日志，不阻断主流程
