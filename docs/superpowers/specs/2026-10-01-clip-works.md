# Spec: 剪辑作品（1:N）+ 剪辑室信息架构重构（clip-works）

> 来源：2026-10-01 用户口述 + 逐条确认（同日多轮）
> 关系：**重构** Spec A（`2026-10-01-audio-lineage.md`）的剪辑室信息架构；把"资料 ↔ 剪辑"从 **1:1 改成 1:N**；新增 hover 快速预览
> 状态：**待用户过目** → 过目后进入 writing-plans

---

## 0.0 为什么（用户判定）

用户原话要点（**这些是已定裁决，不再是选项**）：

1. **"剪辑的作品与资料是一对一的，这个是不对的"**——同一个资料可以有不同的剪法，**一个资料可以有多个剪辑作品**。
2. **剪辑室卡片列表对屏幕利用率很低**（默认一页 10 张卡，宽屏一行能摆 4~5 张，下面一大片空白）→ 改**无限下拉**。
3. **"平铺已经不需要了"**，只保留卡片形态。
4. **"点击进入显示下一层也没有意义"**——卡片点击应该**直接进编辑页**，不再有中间那层列表。
5. **卡片上加删除 icon**，点击触发删除。
6. **卡片上可以预览剪辑内容**："hover 到一张卡上就可以快速预览视频；如果只有音频，还是要显示封面，hover 上去也是直接播放，移开鼠标就停止播放、回到第一帧或者封面"。
7. **toolbar 上要有"声音是否开启"的按钮**（因为 hover 自动播放）。
8. **新建入口两条**：剪辑室 toolbar 的「新建作品」→ 选资料；**资料库 toolbar 的「剪辑」icon** → 以当前资料为底建作品 → 进编辑页。
9. **作品名是临时的**（系统先给一个，用户之后能改）。
10. **删除语义**："删除作品不会删除来源；删除来源之后，编辑就无法编辑了，只保留之前的剪辑作品。"
11. **"删除作品就会删除所有成品"**（以后有改动再说）。
12. **老数据直接删**："8 条老数据，直接删掉，没问题的，现在都是早期阶段，没什么意义。"

**真实痛点**：现在这张"资料卡"其实是三样东西挤在一起——资料（视频文件）、剪辑工程（时间点）、成品（导出的 mp3）。所以会出现"同一部作品有两张卡""点进去才发现是空的""剪了第二条只能覆盖第一条"这类怪象。用户的要求是把它们拆开：**卡片代表"一次剪辑"，资料只是它依赖的素材。**

## 0.1 现状基线（2026-10-01 读码 + dev 库实核）

1. **硬一对一**：`clip_projects.import_id` 是 `NOT NULL UNIQUE`（`server/src/db/schema.ts:66`）——SQLite 里这意味着**一个资料只能有一行剪辑数据**，想建第二条会直接被约束挡下。
2. **段的归属**：`clip_segments.project_id → clip_projects.id`，另有索引 `idx_clip_segments_project`（`schema.ts:71-80`）。
3. **repo 全部按 import_id 操作**（`server/src/db/repo/clip-projects.ts`）：`clearByImportId` / `countSegmentsByImportId` / `list` / `get(importId)` / `upsert(importId, …)` / `delete(importId)`。
   ⚠️ 其中 `upsert` 用的是 **`ON CONFLICT(import_id)`**（`:66`）——**这个写法依赖那个 UNIQUE 约束，去掉 UNIQUE 后它会直接报错**，必须重写。
4. **路由**（`server/src/media/project-routes.ts`）：`GET /api/projects`、`GET|PUT|DELETE /api/projects/:importId`、`POST /api/projects/:importId/export`。
5. **前端详情页按"资料 id"取工程**：路由是 `/studio/:importId`（`web/src/pages/studio-detail.tsx:78` 调 `getProject(importId)`）；保存时（`:119`）**把工程名写成资料标题**（所以现在作品名 = 资料名，两个作品必然重名）。
6. **首页「正在编辑」**读 `clip_projects JOIN imported_sources`（`server/src/db/repo/home.ts:29-42`），点卡进 `/studio/:import_id`。
7. **任务抽屉的标题**按 `payload.importId` 回查资料标题（`server/src/media/jobs-routes.ts:76-84`）。
8. **两处会清空剪辑数据**：换集重下（`ytdlp-routes.ts:212-214`）与**删资料**（`:678`，`clearByImportId`）。
9. **一条休眠路由**：`POST /api/media/:importId/clip`（`media-routes.ts:94`）——web 侧**无任何调用方**（原调用方 `VideoClipPanel.tsx` 已在 P2 删除）。
10. **dev 库实测**（`.sct/dev-data/sct.db`，2026-10-01）：
    ```
    imported_sources 2 行（12、13）｜ source_videos 2 行 ｜ clip_projects 0 行
    audio_items 8 行 —— 全部 source_type='edit'、source_url=''、无任何来源/作品归属
    ```
    → 这 8 条就是"没有任何归属的成品"，按用户裁决**迁移时直接清掉**（见 §0.6）。
11. **剪辑室现状**（Spec A 之后）：卡片 = **资料**（归并键 `source_import_id`）、卡内分「素材/成品」、有「源已删除」卡；两个视图（平铺/剧集分组）+ 下钻层 + 分页（10/20/50，默认 10）。

## 0.3 数据与迁移

**⓪ 迁移前自动备份（只在"真要重建"时做一次）**

- **判据**：仅当检测到需要重建 `clip_projects` 时，把 `<数据目录>/sct.db` 复制为 `sct.db.bak-<时间戳>`（时间戳取**紧凑格式**：`YYYYMMDDHHMMSS`，秒级即可——实现期评审发现原稿写成带 `-` 的 `YYYYMMDD-HHMMSS` 与实现不符，以本行为准）。
- **为什么**：重建与清理**都不可逆**，而这是用户唯一的数据库；这份副本是唯一退路。
- **备份失败**：**继续迁移**，但打 error 日志（不能因为备份失败把用户挡在门外）。
- ⚠️ **不可回退到旧版本**：重建后 `clip_projects` 上不再有 UNIQUE，而旧代码的 `upsert` 用的是 `ON CONFLICT(import_id)` → **旧版服务端在新库上会直接报错**。要回退只能用上面那个 `.bak`（并丢掉它之后的改动）。

**① 重建 `clip_projects`（去掉 UNIQUE，保留 id）**

**整个重建包在同一个事务里**（SQLite 的 DDL 可回滚）。不包事务的后果很具体：若在 `DROP` 与 `RENAME` 之间崩溃，库里只剩 `clip_projects_new` → 下次启动会重新建出一张**空表**（`CREATE TABLE IF NOT EXISTS`）、检测到它带 UNIQUE 又触发一次重建、撞上已存在的残表 → **应用起不来**。

```sql
BEGIN;
DROP TABLE IF EXISTS clip_projects_new;      -- ★ 先收拾上次崩溃可能留下的残表（幂等前提）
CREATE TABLE clip_projects_new (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  import_id INTEGER NOT NULL,                -- ★ 不再 UNIQUE：一个资料可以有多条作品
  name TEXT,
  created_at TEXT NOT NULL DEFAULT (datetime('now')),
  updated_at TEXT NOT NULL DEFAULT (datetime('now'))
);
INSERT INTO clip_projects_new (id, import_id, name, created_at, updated_at)
  SELECT id, import_id, name, created_at, updated_at FROM clip_projects;  -- ★ 显式带 id：段的 project_id 必须继续指得对
DROP TABLE clip_projects;
ALTER TABLE clip_projects_new RENAME TO clip_projects;
-- AUTOINCREMENT 序号对齐（RENAME 会把 sqlite_sequence.name 改成新名；显式插 id 本也会抬高 seq，这里是双保险）
UPDATE sqlite_sequence SET seq = (SELECT COALESCE(MAX(id), 0) FROM clip_projects) WHERE name = 'clip_projects';
COMMIT;
```

- **检测方式**：`SELECT sql FROM sqlite_master WHERE type='table' AND name='clip_projects'` 里是否还含 `UNIQUE` → 含则重建，不含则跳过（**幂等**：跑第二次不再动）。
- **不写 REFERENCES**（与全库一致，库没开外键）。
- **段的 `project_id` 不受影响**：因为 id 原样搬。

**② `audio_items` 加列**（`ensureColumns` 幂等）

```sql
ALTER TABLE audio_items ADD COLUMN source_work_id INTEGER;   -- 指向 clip_projects.id；成品才有，素材/录制 → NULL
```

**③ 把老成品挂回它所属的作品（迁移窗口内 1:1 仍是事实，所以映射唯一、无歧义）**

⚠️ **③ 与 ④ 的执行条件（2026-10-01 实现期裁决，务必照做）**：这两步**只在"本次真的重建了表"时执行**（判据 = `clip_projects` 还是带 UNIQUE 的老库形态）。两个理由：

1. 它们是**老库一次性数据整理**，与重建同生命周期；行删除**与重建放在同一个事务里**（原子：要么都成、要么都回滚），**磁盘文件删除放在提交之后**（IO 不可回滚，失败只记日志）。
2. 更重要的是：**新库里出现"无归属成品"是 bug 信号，不该被自动删** —— 那些行交给 §0.5 的「无作品」安全网展示给用户看（可见 = 可管理）。

这条规则同时解掉了一个真实冲突（实现期实测 4 例失败）：`schema.test.ts` 里**既有的 D8 纠偏用例**（`download` 行被纠偏成 `edit` 后即"edit + 无作品 + 无来源 + `source_url` NULL"）与 **Spec A 的"空串→NULL"用例**（`edit` + `source_url=''`）造出来的行，形态与"该删的老成品"**完全相同**；若每次启动都清理，那些用例的行会被误删，而且 SQL 层面无法区分。

不做 ③ 的后果很具体：老库里由**剪辑路径**产出的成品（`source_url` 非空 → Spec A 回填给了 `source_import_id`）既不会被清理、又没有任何作品可挂 → **在新作品墙里彻底看不见**。

```sql
-- 只在该资料**恰好有 1 个作品**时挂（迁移那一刻 1:1 是事实：老库每条资料最多一个工程）
-- 不满足条件的行保持 NULL，交给 ④ 的清理与安全网
UPDATE audio_items SET source_work_id = (
  SELECT p.id FROM clip_projects p WHERE p.import_id = audio_items.source_import_id
)
 WHERE source_type = 'edit'
   AND source_work_id IS NULL
   AND source_import_id IS NOT NULL
   AND (SELECT COUNT(*) FROM clip_projects p WHERE p.import_id = audio_items.source_import_id) = 1;
```

**④ 清理无归属的老成品（用户裁决 12；同样只在重建那一次执行）**

```sql
-- ★ 条件刻意收窄：只有"编辑产物 + 没有任何归属线索"才清。
--   刻意**不含** source_url 非空的行——那类（如"网址还在、来源已被删"）可能是仍有价值的线索，
--   不在用户授权的范围内（用户只授权删"8 条老数据"那一类）。
DELETE FROM audio_items
 WHERE source_type = 'edit'
   AND source_work_id IS NULL
   AND source_import_id IS NULL
   AND (source_url IS NULL OR source_url = '');
```
- 顺序：先取 `file_path` 清单 → 删 DB 行（**在重建那个事务内**）→ 提交后**再**删磁盘文件（顺序反了就读不到路径）。
- **删文件失败一律不阻断启动**：单个文件删不掉（被占用/权限/已不存在）→ 记日志继续；**整个迁移块包 try/catch，任何异常都不许从 `initSchema` 抛出去**——启动路径上的 IO 失败会直接变成"应用打不开"。
- **必须落盘留痕**：`旧成品清理:删除 N 行,文件删除 M/共 K 个`，且**逐个文件路径按 `info` 级打印**（info 会落进 `logs/<天>/<小时>.log`；debug 只进内存环形缓冲、会被滚掉）。删掉的是用户的文件，事后必须查得到。
- dev 库预期删 **8 行**（老库形态确实会触发重建）。
- 为什么敢自动删：用户明确裁决"8 条老数据直接删掉，没问题"；且这些行在新模型里没有任何入口能看到（不可见 = 不可管理）。

**⑤ 迁移顺序**：`db.exec(SCHEMA_SQL)` → `ensureColumns`（补 `source_work_id`）→ 回填 `source_import_id`（Spec A 的）→ **备份** → **重建 clip_projects** → **老成品挂回作品** → **清理老成品**。每一步幂等；除备份外的写操作都在事务里。
**纪律的边界（别扩大改动面）**：上面"不许抛出去"只约束 **本 spec 新增的三步**（备份 / 重建 / 清理），方法是各自内部包 try/catch。**不等于**给整个 `initSchema` 套一层 try/catch——既有的 D8 历史纠偏与 Spec A 回填维持原样（那两处是既有行为，本 spec 不动它们）。

## 0.4 接口契约

| 方法 | 路径 | 变化 |
|---|---|---|
| POST | `/api/projects` | **新增**。body `{ importId }` → `{ ok, project }`（默认名与序号规则见 D15/D23）。错误：`importId` 不存在/非法 → 404；该资料没有视频素材行 → 404；**素材行在但文件已丢失 → 404 `FILE_MISSING`**（与既有 clip/export 路由同一口径——不让用户建一个注定剪不动的作品）。**每个错误响应都要带 `error.next` 的可执行下一步**（如"回资料库重新下视频"），因为新建作品的弹层只能凭 `has_video` 判断"可剪"，**列不出"素材文件其实丢了"的资料**——挡在前端的那道关是假的，报错必须自己把话说全 |
| GET | `/api/projects` | **改**。每条 = 一个作品，字段：`{ id, import_id, name, updated_at, segment_count, product_count, total_sec, first_segment, source }`。`source` = `{ title, site, kind, has_video } \| null`（null = 资料已删；**刻意不含 `has_cover`**——本仓惯例是不用它当渲染开关，卡片有来源记录就试取图、失败由 `onError` 回退纯色底，见 `web/src/api.ts` 的同类说明）；`first_segment` = `{ start_sec, end_sec } \| null`（供 hover 预览）；`total_sec` = 各段时长之和 |
| GET | `/api/projects/:projectId` | **改**（参数从 importId 换成作品 id）。返回 `{ id, import_id, name, updated_at, segments[] }`；作品不存在 → 404 |
| PUT | `/api/projects/:projectId` | **改**（同上）。body `{ name, segments }`；全量替换段（事务不变）。**`name` 是空白串 → 存 `null`**（沿用既有 PUT 的口径）；`segments` 允许空数组（= 清空剪辑点） |
| DELETE | `/api/projects/:projectId` | **改**（同上）+ **连带删该作品的全部成品（DB 行 + 磁盘文件），同事务**（D6）。返回 `{ ok, deleted, deleted_products }` |
| POST | `/api/projects/:projectId/export` | **改**（参数换成作品 id）；job payload 增加 `projectId` 与 `workName`（D19） |
| GET | `/api/audio?project=<projectId>` | **新增查询参数**（D17）：只回该作品的成品；不传 → 维持现状（全部）。**传入不存在/非法的 id → 返回空列表，不是 404**——它是列表过滤，不是资源寻址 |
| DELETE | `/api/audio/:id` | **不变**（单条成品删除走它） |
| DELETE | `/api/imports/:id` | **改行为**：**不再调 `clearByImportId`**（D7：作品与成品保留） |
| POST | `/api/media/:importId/clip` | **不动**（D20） |

**受影响的调用点（必须一起改）**：`web/src/api.ts`（`getProject/listProjects/putProject/deleteProject/exportProject` 的参数语义 + 新增 `createProject`）、`web/src/pages/studio-detail.tsx`（按路由 `:projectId` 取数、保存时**不再把资料标题当作品名**）、`web/src/pages/index.tsx`（首页链接与文案）、`server/src/db/repo/home.ts`（editing 查询）、`server/src/media/jobs-routes.ts`（标题回退加 `workName`）。

## 0.5 UI 规格

### 剪辑室（作品墙）

```
┌ toolbar ─────────────────────────────────────────────────────┐
│ [+ 新建作品]                       🔊/🔇 预览声音   共 N 个作品 │
├──────────────────────────────────────────────────────────────┤
│ ┌────────┐ ┌────────┐ ┌────────┐ ┌────────┐                 │
│ │ 封面    │ │ 封面    │ │ 封面    │ │ 封面    │   ← auto-fill  │
│ │ 作品名  │ │ 作品名  │ │ 作品名  │ │ 作品名  │                 │
│ │ 资料名  │ │ 资料名  │ │ 资料名  │ │ 资料名  │                 │
│ │成品2条·3段│ │成品0条·1段│ │…      │ │…       │                 │
│ └────────┘ └────────┘ └────────┘ └────────┘                 │
│                     ↓ 滚到底自动加载下一批（20 条/批）          │
└──────────────────────────────────────────────────────────────┘
```
（卡片上的摘要是**一行**：`成品 N 条 · N 段 · 共 mm:ss`；卡片窄时允许折行）

- 卡片整张可点（键盘 Enter/空格同样可进）、右上角删除 icon（`stopPropagation`）。
- **资料已删除**的作品：卡片打灰色标签「资料已删除」，封面回退纯色底；点进去是"只读编辑页"（§编辑页）。
- 删除弹窗（`Modal.confirm` + `okType:'danger'`）：`删除《作品名》？` + 正文 `将同时删除它的 N 条成品（音频文件一并删除），不可恢复。` + 确认/取消。
- 空态（一个作品都没有）：antd `Empty`「还没有剪辑作品」+ 主按钮「新建作品」。
- **搜索框保留**（本 spec 没提它 → 不删功能）：按**作品名 / 所属资料名**过滤；过滤/清空时把"已渲染批数"重置回第一批。
- **「无作品」安全网分组**：列表**末尾**，**仅当存在"无作品成品"时才渲染**（`GET /api/audio` 里 `source_work_id == null` 且 `source_type === 'edit'` 的那些）。正常情况下它永远为空（迁移已清理 + 新流程保证成品必有作品），所以它不是常驻 UI，而是一道**防"数据静默消失"的网**：万一日后又有代码路径产出无作品成品，用户仍能看见、试听、单条删除，而不是像那条清理理由说的"不可见 = 不可管理"。

### hover 快速预览（D11）

| 项 | 规格 |
|---|---|
| 触发 | 鼠标进入卡片 **停留 400ms** 才起播；400ms 内移开 = 什么都不发生 |
| 有视频 + 有剪辑点 | 播放**第一段**（`currentTime = first_segment.start_sec`，播到 `end_sec` 停） |
| 有视频 + 无剪辑点 | 播视频**开头 5 秒**（从 0 播到 5s 或素材结束） |
| 资料已删 / 无视频 | 只静态显示封面，不播 |
| 播放载体 | 卡片封面区内嵌 `<video muted playsinline preload="none" src="/api/media/:importId/file?token=…">`（复用既有 Range 路由）；无视频但有成品时改用 `<audio preload="none">` 播**最新一条成品** |
| 移开鼠标 | 立刻 `pause()` + `currentTime` 回到起点；**并卸载该元素**（`<video>`/`<audio>` 不留着） |
| 并发 | **同一时刻只有 1 张卡在播**：新的一张起播前，先把前一张停掉并卸载 |
| 声音 | 默认**静音**（`muted`）；toolbar 开关打开后才有声（状态存设置表，D12） |
| **有声预览 × 浏览器自动播放策略** | 浏览器禁止"没来由的自动播放"。**静音起播是允许的**；要出声时：① 用户**点开关那一下**算一次用户交互 → 在该次点击里对"即将用于预览的元素"做一次静音→出声的播放尝试（把交互"花"在解锁上）；② 即便如此仍可能被拒 → **`play()` 的 Promise reject 时回退为静音播放** + `logFe('debug', …)`，不弹错（进度条照走，用户看得出在预览）。**验收必须含一条人工项：打开声音后 hover 真的有声音**（Electron 的策略与普通浏览器可能不同，不能只按浏览器假设） |
| 静音时的反馈 | 卡片封面区显示一条细进度条（表示"正在预览"），否则只有音频的卡静音时看不出任何变化 |
| 失败 | 视频/音频加载或播放失败 → 回退到封面 + 进度条不动（`logFe('debug', …)` 留痕，不弹错误）；**不得让失败的元素留在 DOM 里继续占资源** |

### 编辑页（`/studio/:projectId`）

- 进去按 **作品 id** 加载；新作品 `segments` 为空（时间轴空，符合用户预期）。
- 顶栏：**可编辑的作品名** + 保存 + 导出 + 打开导出目录 + **「预览音频」按钮**（试听该作品最新一条成品；没有成品则禁用并 tooltip 说明）。
- 时间轴/波形/胶片条：**不变**（仍按资料的 `importId` 取派生图）。
- **成品明细**（新）：该作品已导出的音频列表，每条 = 标题 + 格式/时长 + 播放 + 单条删除（`Modal.confirm`）；空态 `Empty`「这个作品还没有导出过成品」。
- **资料已删除时**：顶部一条 `Alert`「资料已删除，无法再编辑；已导出的成品仍可试听与删除」，时间轴与保存/导出禁用，成品明细照常可用。

### 新建作品（两条入口）

1. **剪辑室 toolbar「新建作品」** → 弹层（antd `Modal` + 列表）列出**可剪的资料**（有视频素材的；带封面、标题、素材状态）→ 选中 → 创建 → 跳编辑页。没有可剪资料时，弹层内给「去资料库下视频」的引导。
   （**数据源复用既有 `GET /api/imports`**——它已经带回 `has_video` / `thumbnail` / `material_entry_index`，不需要新端点。）
2. **资料库 toolbar「剪辑」icon** → 对当前选中的资料直接创建 → 跳编辑页。该资料没有视频素材时按钮禁用 + tooltip「先下载视频素材」。

## 0.8 验收清单

**图例：`[自动]` = 单测/脚本可断言；`[人工]` = 需真机 GUI 目验（子代理起不了 Electron，一律交用户）。**
**构造前提**：第 1 / 2 / 4 / 6 / 9 / 10 / 11 条**必须先造 fixture** —— dev 库 `clip_projects` 是 **0 行**、`audio_items` 那 8 行又会被清理，不造数据这些验收就是空洞的。构造方式：`openDatabase` 建库 → 插 1 个资料 + 1 个作品 + 2 个段（记下 id 与段数）→ 再跑一次 `initSchema` 触发迁移。

1. `[自动]` 老库升级后：`clip_projects` 建表 SQL 里**不再有 UNIQUE**；**已有作品的 id 不变**，其 `clip_segments` 一条不少（迁移前后 `COUNT(*)` 相等）。
2. `[自动]` `initSchema` 连跑两次：表结构不再变、老成品不再被重复清理（幂等）；且**第二次不再生成新的 `.bak`**。
3. `[自动]` `audio_items` 出现 `source_work_id` 列。
4. `[自动]` 同一个资料**能建出第二个作品**（旧版会被 UNIQUE 挡住）；两个作品各有自己的剪辑点，互不覆盖。
5. `[自动]` 默认名形如 `《资料名》 的剪辑`，同资料第二个是 `《资料名》 的剪辑 2`；删掉 2 号再建得 ` 2`（**序号会回收**，见 D23：同名的已被删，不存在撞名）；编辑页能改名并保存成功。
6. `[自动]` 导出一条成品后：`GET /api/audio?project=<id>` 只回该作品这一条；`audio_items.source_work_id` = 该作品 id，且 `source_import_id` 与之一致。
7. `[自动]` 删作品：该作品行、它的段、它的成品行都没了；**其它作品的成品不受影响**。
8. `[自动]` 删资料：`imported_sources` 与 `source_videos` 行没了，**该资料的 `clip_projects` 行与成品行都还在**。
9. `[自动]` 换集重下：该资料下所有作品的段被清空，作品行与成品都还在。
10. `[自动]` **导出在途删作品**：起一个导出 job（不 await）→ 删掉该作品 → job 结束时**不得**写入成品行，job 置 error 且 message 说明原因。
11. `[自动]` 迁移清理：只删"`edit` + 无作品 + 无来源 + `source_url` 空"的行；**另造一条"`source_url` 非空但来源已删"的 edit 行，断言它不被删**。
12. `[自动]` `pnpm typecheck` 三包 0 错；`pnpm --filter @sct/server test` 全绿；`web` / `desktop` build 成功。
13. `[人工]` 剪辑室：只出现作品卡（没有资料卡、没有平铺视图、没有下钻层）；卡片显示 `成品 N 条 · N 段 · 共 mm:ss`。
14. `[人工]` 无限下拉：作品 > 20 个时首屏 20 张、滚到底追加；切走再切回（焦点重拉）**不跳回顶部**；滚动不抖。
15. `[人工]` hover 预览：停留 400ms 起播；快速划过一排卡**不会同时起播多个**；移开立刻停并回到起点；只有音频的卡显示封面 + 进度条。
16. `[人工]` **打开"预览声音"后 hover 真的有声音**（Electron 策略可能与浏览器不同）；关掉后静音；重启应用开关状态还在。
17. `[人工]` 三处确认文案：删作品说清"将同时删除 N 条成品"；删资料说清"作品与成品会保留"；换集说清"N 个作品、M 个剪辑点将被清空"。
18. `[人工]` 首页「正在编辑」列的是作品、点卡进对应编辑页；任务抽屉里的导出任务标题显示**作品名**。
19. `[人工]` 资料已删的作品：卡片带「资料已删除」标签；编辑页只读，成品明细仍可试听 / 可删除。
20. `[人工]` 首次迁移启动：`.bak` 备份文件真的生成；日志里能看到清理那行（**含被删文件路径**）。
